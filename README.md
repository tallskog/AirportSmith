# AirportSmith

A Windows desktop editor for producing customized versions of default MSFS 2024 airports — edit a stock airport's runways, taxiways, and parking, then package the result as a Community-folder add-on that overrides the sim's built-in version at that ICAO.

**Status: v0.1 — read-only extraction, plus early editing and XML export.** AirportSmith can connect to a running MSFS 2024 session via SimConnect and display an airport's runways, frequencies, taxi parking, taxiway path network, and jetways for a given ICAO. An **Edit** tab lets you change a taxi path's name, type, associated runway number/designator, left/right edge type, left/right edge lighting, and center line/center line lighting, and a runway's edge light intensity, VASI/PAPI type+angle, and approach light system, then save those edits as a project you can reload later without MSFS running. An **Export Airport XML** button produces a `bglcomp.xsd`-conformant `<Airport>` XML file for the edited airport — ready to compile with the MSFS 2024 SDK's `bglcomp` or import into the Dev Mode Scenery Editor to actually override the stock airport. **Packaging a Community-folder add-on from that XML is not yet implemented** — see [`requirements.md`](requirements.md) for the full roadmap (including this export feature's known limitations), and [`CLAUDE.md`](CLAUDE.md) for the domain research summary and project conventions.

## Usage

1. Start MSFS 2024 and load into any session (the main menu is sufficient — an aircraft/flight does not need to be active).
2. Launch AirportSmith, type an ICAO code, and click **Load Airport**.

In Debug builds only, two extra buttons appear: **Export Debug Data** (once an airport is loaded) saves the loaded data as JSON to a temp folder (`%Temp%\AirportSmith-dev`) for manual inspection/debugging — files are kept across app runs, not deleted on exit. **Load Debug Data File** opens a file picker on that same folder and loads a previously exported JSON file back in, without needing MSFS running. Neither button is present in Release builds.

A **Diagram** tab shows a top-down rendering of the loaded airport's runways (labelled with their designation, e.g. "09L"; a displaced threshold, if present, marked white per FAA AIM 2-3-3 with a threshold bar and arrow; a blast pad/overrun, if present, shown in a lighter slate gray than the runway with a yellow demarcation bar and chevrons per AIM; an approach light system, if present, shown as a schematic gold light rail (a connecting line plus individual light markers, so it stays visible even at a large airport's fit-to-view zoom) extending out from the threshold per FAA AIM 2-1-3, with a red crossbar for ALSF-1/ALSF-2 systems), taxiways (pavement bands with a centerline — solid blue and labelled with the taxiway name if named, dashed gray if not, a quick visual check for missing taxiway names; a taxi path associated with a runway instead draws its centerline as a thick red line, so it's easy to tell apart from an ordinary taxiway and to sanity-check its position — real OIBK data has a few of these running several hundred meters), parking spots, and every distinct taxi point (a small red dot) resolved from the airport's taxi paths, including ones only reachable via such a runway-associated path. It starts fitted to the window; scroll the mouse wheel to zoom in/out around the cursor and hold the left mouse button to drag the view around. Taxiway/parking positions depend on `TAXI_POINT`/`TAXI_PARKING` bias-coordinate fields that are not yet confirmed against a live sim, so that part of the diagram may be empty or look wrong until verified — see `requirements.md`'s Known gaps for the Diagram epic.

An **Airport Data** tab shows a raw, expandable tree of every field extracted for the loaded airport — every runway, frequency, parking spot, taxi path, and jetway, including nested sub-structures like a runway's VASI/PAPI or approach light system — so you can check exactly what data is (and isn't) present for a given airport (e.g. whether a runway actually has an approach light system before expecting the Diagram tab to draw one) without it being limited to what a given tab's DataGrid already shows as columns. Enum-backed raw values the SDK documents with a name per number but that aren't (yet) a real C# enum type (frequency type, parking spot type/name/suffix, a taxi path's associated runway number) show that name alongside the number, e.g. "Type: 6 (TOWER)"; fields that are real enums (approach light system type, VASI/PAPI type, taxi path type/runway designator/left/right edge type) just show their name directly, e.g. "SystemType: Calvert".

An **Edit** tab lets you edit the loaded airport, with the diagram shown alongside the grids for spatial context and kept in sync as you edit — renaming a taxi path immediately updates its label and named/unnamed styling in the diagram, no reload needed. A **Taxi Names** panel manages the shared, user-editable list of taxiway names (add/rename/delete) — renaming or deleting one is reflected everywhere it's used, including every diagram label for paths that share it. A blank entry shows as "(no name)" in gray italics rather than an empty row — it's a real sim entry that taxi paths with no name (e.g. ones leading to parking) legitimately share, often dozens at a time, so it's worth knowing before renaming it that doing so will rename all of them; it's still directly editable if you do want to give it a real name. Each taxi path row's first column is a "Hide from Diagram" checkbox that hides just that taxiway from the diagram for decluttering a busy airport (display-only — never saved); it also picks its name from the shared list (not free text), shows the sim's own Start/End taxi point indices (read-only, cross-referencing the Taxiway Points grid below), and has pickers for type, associated runway number/designator, and left/right edge type, plus checkboxes for left/right edge lighting and center line/center line lighting. Every column has its own filter right in its header — a text box for Name/Start/End/Rwy # (matches as a substring), a dropdown with a leading "(any)" for every enum/checkbox column — and they all combine together; a "Clear Filters" button next to the grid resets them all at once. Selecting one or more rows in the grid highlights the matching taxiway(s) in the diagram. You can also click one or more taxiways directly in the diagram (Ctrl+click to select several — only taxiways, not runways, can be selected this way) to filter the grid down to just the selected path(s); a plain click on empty diagram space clears the selection and shows every path again. With a selection active, right-click the diagram to batch-edit the selected path(s) via a popover — the popover only changes whatever field(s) you actually touch (leave a field blank/indeterminate and it's left exactly as-is on every selected path, never overwritten from another selected path's value); Apply or Cancel both clear the selection afterward. While that popover is open, grid row clicks stop driving the diagram highlight (Apply or Cancel first) — otherwise an incidental click to check something in another row would silently hijack the selection your batch edit is about to apply to. Each runway row also starts with its own "Hide from Diagram" checkbox, then sets edge light intensity, VASI/PAPI type and glideslope angle (per end/side), and approach light system (per end). A **Taxiway Points** grid lists every distinct taxi point (the same ones drawn as red dots on the diagram) with its index and X/Z position, plus pickers for its type (e.g. hold-short) and orientation — editing either updates every taxi path that shares that point, so they never disagree with each other. A "Hide All from Diagram" checkbox next to the grid header hides or shows every point at once (there can be hundreds, so there's no per-point checkbox); clicking one or more red dots on the diagram (Ctrl+click for several) filters the grid down to just the selected point(s), independently of any taxiway path selection — a plain click on empty diagram space clears both selections. Edits apply immediately to the loaded airport. **Save Project** writes them to a project file under `%LocalAppData%\AirportSmith\Projects\{ICAO}.json` (`%LocalAppData%\AirportSmith-dev\...` in Debug builds); **Load Project** reloads a previously saved project for the typed ICAO without needing MSFS running — a project saved by an older version of AirportSmith is migrated automatically, never silently dropped.

Once you're happy with your edits, **Export Airport XML** (next to Load Project, in the main toolbar) prompts for a save location and writes a `<FSData><Airport>...</Airport></FSData>` document that overrides the stock airport's runways and taxiways/parking with your edits — the exported path is shown underneath the toolbar. If anything had to be skipped, truncated, or defaulted while building the file (an unmapped surface/parking code, a taxi name over 8 characters, a taxi path type with no XML equivalent, etc.) it's listed right there too, rather than silently dropped — see `requirements.md`'s "Generate SDK-compatible `<Airport>` XML" epic for the full list of known limitations (e.g. hold-short taxi point markings and jetways aren't carried over). Packaging the exported XML into an actual Community-folder add-on is still a separate, not-yet-implemented step — see `requirements.md` for that epic.
